Methodology

How this observatory works

A capstone project in rigorous data practice. Every number traces to a named source, a stated limitation, and a provenance record. No figure is fabricated or estimated.

Core principle
The Nigerian Student Diaspora Observatory was built around a single non-negotiable rule: every number displayed must trace to a real, verifiable, named source. The system has no estimate engine, no interpolation, and no fallback defaults. When data does not exist, the system says so explicitly. The absence of a number is itself a finding, and the Documented gaps list on the dashboard is a first-class output, not a placeholder.
This stands in contrast to most data dashboards, which silently fill gaps with estimates, present projections alongside actuals without distinction, or aggregate across incompatible measurement instruments. The NSDO separates those concerns by construction.
Data integrity rules
1 — Provenance on every record
Every dataset is linked to a named source (organisation, URL, publication date) and a metric definition that describes exactly what was counted and how. Datasets cannot exist without stating their limitations. The limitations field is enforced non-empty by the API.
2 — No overwriting historical data
Datasets are immutable after import. Identity fields (source_id, destination_country, reference_period, metric_definition_id) cannot be changed. Corrections create a new dataset linked via superseded_by_id; the original is deprecated, not deleted.
3 — Gaps are null, never zero
If a count for a period does not exist, the system returns null. Charts show a visible gap in the line. Growth calculations for gap periods return null, not an estimated delta. Known gaps are documented in seed_data.py:KNOWN_GAPS and surfaced on the dashboard.
4 — Comparability is always explicit
Numbers from different metric definitions (e.g. HESA UK headcount vs IIE Open Doors US count) are never silently placed on the same axis as like-for-like figures. Every cross-metric display carries a ComparabilityVerdict and a plain-English reason explaining the methodological difference.
5 — No synthetic data in production
Test fixtures are clearly labelled SYNTHETIC_DO_NOT_TREAT_AS_REAL.csv. Seed data carries exact citation sources and year-specific provenance. No figure on the dashboard was generated, estimated, or interpolated by this system.
Comparability verdict system
Every analytical result — trend series, snapshot table, comparison endpoint, dashboard chart — is assessed against a three-valued comparability verdict. The verdict and its reason are always returned as part of the API response and always displayed in the UI.
Comparable
Same metric_definition_id and same characteristic profile. Direct numerical comparison is valid.
Methodology differs
Different enrolled-headcount instruments (e.g. HESA vs Open Doors), or same metric but different characteristic breakdown profiles. Comparison is informative but not like-for-like. Always displayed with a warning.
Incomparable
Unverified source, global aggregate, or a metric with no disclosed methodology. Must never be charted on the same axis as official enrolled-headcount figures.
Characteristic profiles and aggregation
A dataset with a bare total (no sub-dimensions) and a dataset broken down by mode_of_study are not directly aggregable even if they share a metric definition. The bare total may already include all mode-of-study slices; summing them would double-count. When characteristic profiles differ between periods in a trend series, the API returns series_comparability: "profile_varies" and a human-readable series_note.
Data sources and reliability tiers
Four reliability tiers are assigned to each source based on its institutional mandate, independence from the data subjects, and disclosed methodology.

Metric definitions
A metric definition specifies exactly what a numeric observation measures. Two observations sharing a metric_definition_id can be directly compared; two with different IDs cannot, even if both describe "Nigerian students abroad".

Calculation conventions
Period-over-period growth
Percent change is computed as (current − previous) / previous × 100, rounded using Python's round() with round-half-even (banker's rounding) to 2 decimal places by default (configurable via the decimal_places query parameter).
Example from verified UK data: 10,810 → 13,020 = +20.44% (raw: 20.4384…%). The raw value and the rounded value are both available in the API response.
Gap handling
A growth point with a gap predecessor always returns percent_change: null. The system never skips a gap to compute growth against the last non-null value without explicit documentation in the API response. The growth series always has the same length as the trend series.
Authentication and access control
All read (GET) endpoints are public. Viewing, analysing, and exporting data requires no authentication. This reflects the nature of published academic research data.
Write operations — importing data, creating or modifying source records, seeding the database — require an admin token obtained via POST /api/auth/token. Sign in →
The first user to register automatically becomes admin. Subsequent users require an existing admin to register them. There are no self-service admin escalation paths.
Technical architecture
Stack
PostgreSQL 16 · SQLAlchemy 2.0 ORM · FastAPI 0.115 · Pydantic v2 · Python 3.12 · Uvicorn · Vanilla HTML/CSS/JS frontend. All backend analytics logic is implemented as pure Python functions with no framework dependency, making every analytical rule independently testable.
Test coverage
202+ tests across 7 test suites plus 3 integration verification scripts. Test suites cover: CSV import pipeline, XLSX import, column mapping and ambiguity resolution, observation characteristics, validation rules, analytics comparability logic, growth rounding, snapshot exclusion rules, gap handling, and seed integrity checking. All tests verifiable without a running database or external network.
Migrations
Three sequential plain-SQL migrations apply at first Docker boot: 001 (7-table base schema) · 002 (observation dimension columns) · 003 (observation_characteristics table). No Alembic runtime dependency at startup — migrations run via Postgres's docker-entrypoint-initdb.d.
